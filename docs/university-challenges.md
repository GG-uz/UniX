# Университетские вызовы (4.1)

## Подключение

1. На **отдельном тестовом Supabase-проекте** с миграциями `0001–0003` после согласования
   выполните в SQL Editor **целиком, по одному файлу**: `0004_university_authority.sql`,
   `0005_university_challenges.sql`, `0006_challenge_permissions_rpc.sql`. При ошибке остановитесь.
   Это однократные транзакционные миграции. Не добавляйте `unix_private` в exposed schemas.
   Data API должен видеть `public`; требуется PostgreSQL 15+ для security-invoker view.
2. В профиле **уже проверенного** `SUPER_ADMIN` откройте `/admin` → «Администраторы университетов».
   После внешней проверки полномочий укажите UID подтверждённого пользователя и его вуз.
   Несовпадение вуза и самоназначение запрещены. Эта операция не меняет `profiles.role`.
   При отсутствии платформенного администратора остановитесь и согласуйте его отдельное provisioning.
3. Администратор на `/challenges` увидит ссылку в `/university/dashboard`. Там можно искать
   подтверждённых студентов своего вуза, назначать и отзывать капитанов отдельно по дисциплинам.
   Один человек может иметь несколько назначений. `STUDENT_CAPTAIN` в профиле не является назначением.
4. Проверьте под отдельными согласованными тестовыми аккаунтами студента, капитана и администраторов двух вузов.
   Для production нужно отдельное решение о миграциях и назначениях. Новых переменных среды нет.

## Состояния и видимость

- `/challenges` читает `challenge_feed` с RLS базовой таблицы (публикации, без UID).
  `/demo/challenges` и исторический `/api/challenges` работают на демоданных и ничего туда не пишут.
- Сессия проверяется на сервере, все изменения — через RPC, повторно проверяющие `auth.uid()`,
  почту, членство и область назначения. Доверенные функции используют пустой `search_path`;
  обычным пользователям не выданы права записи в таблицы. Изменения назначений и решений журналируются.
- По умолчанию капитан создаёт `PENDING_APPROVAL` с запросом `CREATE`; одобрение **его вуза**
  публикует `OPEN`, отказ или отзыв назначения отменяет неопубликованный вызов. В независимом
  режиме капитан публикует сразу. Администратор своего вуза действует напрямую в обоих режимах.
- Для `OPEN` разрешён ответ другого вуза, для адресного — только указанного. Заявка `ACCEPT`
  не резервирует вызов. Публикация и принятие требуют отдельных решений разных вузов.
  Переключение режима не изменяет ранее принятые решения и не одобряет ранее поданные заявки.
- Любая операция изменения принимает транзакционную блокировку для вуза. Прямое принятие
  и одобрение принятия берут `FOR UPDATE` одной строки вызова, проверяют срок и допустимость
  после ожидания. Побеждает первая завершившаяся успешным commit транзакция: `ACCEPTED`, один
  `opponent`, остальные ожидающие заявки `INVALID`. Откат не занимает место. Повторный вызов
  создания с тем же UUID не создаёт дубликат. Принятие не создаёт счёт, платёж или результат.
- Отзыв назначения блокирует одобрение его незавершённых заявок даже после нового назначения.
  Администратор создателя может отменить открытый или ожидающий вызов. Истечение (`EXPIRED`)
  вычисляется при чтении и проверяется в RPC по часам БД; cron не нужен. Дедлайн — раньше из
  30 дней и конца предложенного дня в `Asia/Tashkent`. Кабинет показывает последние 100 вызовов.
- Настройка режима сейчас на вуз; решение сосредоточено в `unix_private.needs_approval`.
  Для исключений по дисциплине туда можно добавить lookup по `(university, discipline)`.

## Изолированные проверки

`npm run test:challenges` запускает миграции с нуля в PGlite (PostgreSQL/WASM в памяти)
с тестовым аналогом `auth.uid()` и SQL-ролями `anon`/`authenticated`. Это не тест JWT Supabase.
Проверяются реальные ограничения таблиц, RLS, RPC, последовательные конфликтующие решения,
отзыв и отсутствие полномочий. Эта БД поддерживает одно соединение: она не тестирует гонки.

Для проверки гонок запустите Docker Desktop с Linux-контейнерами, подготовьте локальный образ
`postgres:16` (`docker pull postgres:16`), затем повторите `npm run test:challenges`.
Второй тест использует одноразовый контейнер без сети и два процесса psql; не принимает внешний
URL БД. Он проверяет, что второй процесс действительно ждёт блокировку, до commit первого,
для прямого принятия и согласований. Если движок недоступен, тест явно помечен `SKIP`.
